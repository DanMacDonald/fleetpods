Connected is only one milestone

The radio link, the Apple control handshake, the A2DP transport, a usable PipeWire output, and audio ownership are separate pieces of readiness.

A profile is a capability

A2DP is the music playback service. AAC is the codec used here. A sink is the output the browser stream is routed into. They are three different things.

Ownership chooses the source

The iPhone can be connected alongside XPS. FleetPods asks the pods to give XPS audio ownership, then reacts to the pods’ reports. A request alone does not prove sound is flowing.

Where the microphone fits

Ordinary Bluetooth headset calls can use HFP. FleetPods also implements a separate high-resolution AirPods Pro 3 microphone path: microphone packets arrive over the Apple control connection, FleetPods decodes them, and a PipeWire source exposes them to recording apps. That reverse path is distinct from YouTube’s A2DP playback path.

Pods microphone→Apple control socket→FleetPods decoder→PipeWire source→Recording app

The faster-start change establishes HFP signaling when supported; it does not select the headset audio profile or start microphone capture. YouTube stays on A2DP.

What runs in parallel?

Once the Bluetooth link is up and playback is wanted, A2DP setup can overlap the Apple control handshake. FleetPods does not wait for every control notification before asking for the audio service.

What must wait?

The hands-free request waits for A2DP success and ServicesResolved. Asking sooner returned “connection busy” in our test. The audio sink also has to exist before we can move the browser stream to it.

Why mute the speakers?

FleetPods holds the stream during acquisition so audio does not keep sounding on the speakers. Muting audio does not pause the video clock. During output recovery, FleetPods explicitly pauses and later resumes the player.

What changes during an iPhone → XPS handoff?

If the Bluetooth link and control socket survived, FleetPods reuses them. It asks for ownership and, if the audio output needs recovery, pauses the player, restarts or rebuilds the output, relinks the stream, starts the output, and resumes after the Start command succeeds. A later streaming check verifies progress. If the Bluetooth link was dropped, link and profile setup have to run again.
